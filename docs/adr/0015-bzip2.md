# ADR-0015: Use bzip2 for NEXRAD Chunk Decompression

## Status
Accepted

## Context
NEXRAD Level II real-time chunks and Archive II volume files wrap their message stream
in one or more `BZh9`-tagged BZ2-compressed blocks (see `docs/architecture/nexrad-binary-format.md`).
This is a fixed property of the wire format defined by the ICD, not a choice this project
makes — every chunk emitted by the RDA (radar data acquisition system) is BZ2-compressed,
and there is no uncompressed alternative to decode instead.

BZ2 was added to `crates/radar-workstation` (`chunk.rs`, `decompress_chunk` /
`decompress_blocks`) before this ADR existed, which the dependency audit behind
ADR-0014 flagged against the `CLAUDE.md` "ask first" instruction. This ADR closes that
gap by recording the decision that was already made in code.

Rolling a BZ2 decoder by hand was considered and rejected: BZ2 (Burrows-Wheeler
transform, move-to-front, Huffman coding, run-length encoding, layered together) is
materially harder to implement correctly than either the NEXRAD binary format
(ADR-0008) or the HTTP/1.1 client (ADR-0014) — both of which *are* hand-rolled in this
project. The ownership-cost tradeoff that favors owning simple, well-specified formats
runs the other way for a general-purpose compression algorithm with a large surface for
subtle correctness bugs (and, historically, security bugs) in decoders written by
non-specialists.

## Decision
The `bzip2` crate (`bzip2 = "0.6"`) is used for BZ2 decompression, via its
`read::BzDecoder` streaming reader.

`bzip2` 0.6, with no non-default features enabled, resolves to `libbz2-rs-sys` — a
pure-Rust rewrite of the decompressor, not a binding to the C `libbzip2` reference
implementation. See the erratum below; the paragraph this replaced described the crate's
older C-backed default.

## Consequences
- **No C dependency is added.** `libbz2-rs-sys` is pure Rust; see the erratum below.
  Decompression correctness is still delegated to a third party rather than owned, unlike
  the NEXRAD message parsing immediately downstream of it — that tradeoff stands as
  originally argued (BZ2 is a general algorithm, not a project-specific format) — but it
  no longer costs a C dependency to make.
- `chunk.rs` decompresses to an in-memory `Vec<u8>` per chunk (bounded by chunk size,
  ~120 radials), not a streaming pipeline. This matches the existing chunk-at-a-time
  ingest model and requires no further work from this ADR.

## Erratum (added during documentation remediation, 2026-07-30)

1. **The Decision and Consequences originally asserted `bzip2` wraps the C `libbzip2`
   via `bzip2-sys`. That was wrong at the time this ADR was written and remains wrong
   for the version pinned.** `Cargo.lock` shows `bzip2 0.6.1` depending on
   `libbz2-rs-sys 0.2.5`, not `bzip2-sys`, and `docs/dependency-inventory.md` §3
   independently recorded `bzip2 0.6.1` as "pure Rust" via `libbz2-rs-sys`. The `bzip2`
   crate's default backend changed to the pure-Rust rewrite ahead of this ADR's
   original context section, which was written against the older C-backed default and
   never re-verified against the resolved dependency graph. Net effect is strictly
   better than what was originally decided: the BZ2 decompression step on the
   attacker-influenced chunk-bytes path has **no C dependency at all**, and `ring` (via
   `rustls`) is the only non-Rust code anywhere in the production graph — see
   `docs/dependency-inventory.md` §3. The core argument for *depending on a third party
   rather than hand-rolling BZ2* is unaffected; only the claimed implementation
   language was wrong. Found opportunistically during the W5 requirement/ADR sweep of
   `docs/plans/documentation-remediation.md`, not part of that plan's original scope.
